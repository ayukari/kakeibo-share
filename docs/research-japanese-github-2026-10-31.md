## 3. 精算・端数（うちとの比較）

- **うちの決まり**: 均等割りの余りの円は、メンバーの並び（参加日時→ID）の先頭から 1 円ずつ（`equal_split`、`20261028000200_functions.sql`）。家族ではオーナーがいつもかぶる。
  - 試算（3 人で 1 年 720 件）: うちの決まりでは 478 円 / 230 円 / 0 円。払った人がかぶると 269 / 206 / 233 円、ハッシュで順を決めると 222 / 238 / 248 円。
- **日本のアプリで多いのは「払った人がかぶる」**（pairbo・okanjo・たてかえ侍）。ただし払った人が割る人に入っていないと端数の行き場がなく、pairbo では 1000 円を 3 人で割ると合計 999 円になる。変えるならこの場合の決まりが要る。
- 立て替えが何件もあるとき、okanjo は全件を分数で足してから 1 回だけ丸める（1 件ずつ丸めるより偏らない）。
- 10 円・100 円単位: 各人の差し引きを、合計 0 のまま丸め直して調整額を見せる（tabiwari）。人ごとに四捨五入すると合計がずれる（keento0809 の悪い例）。
- 端数の設定は 3 つに分かれる（sen-ltd の記事）: 丸め方・何円単位か・差額を誰に寄せるか。
- 送金回数: うちと同じ貪欲法でも 3 人以下なら必ず最小。家族なら今のままでよい。
- 傾斜: うちの ratioSplit は重みには対応。「この人は決まった額、残りをみんなで」（「個人分を引いて折半」）はできない。
- 収入の比で精算（duo-pocketbook）: 精算後に手元に残る額が比重どおりになる振込額 `t=(wB·netA−wA·netB)/(wA+wB)`。

## 4. 月の区切り・繰り返し・祝日

- **給料日始まり**（KakeiBon #24・#57、MIT。仕様をそのまま使える）
  - 起算日 D は 1〜31。D がない月は末日。期間は始まりの月で呼ぶ（起算日 25 なら「5 月期＝5/25〜6/24」）。表示に日付を添える。
  - 起算日が土日祝なら「そのまま／直前の平日／直後の平日」から選ぶ。前の期間の終わりは「次の始まり−1 日」。
- **うちの繰り返し**は毎週・毎月・毎年だけ（`recur_freq`）。足すとよいもの: N か月ごと、第 N 何曜日、祝日でずらす、回数で終える。
  - 失敗例: 「今後の分だけ変える」で今月分が二重にできる（PairMoney #330・#249）。足すならテストを書く。
- ほかの実装: guchi-apps/asset-manager（ライセンスなし）は 12/31・1/2・1/3（銀行の休み）も営業日から外し、ずらして月をまたいでも期間を正しく決める。KakeiBon のテストには「25 日が日曜→23 日の金曜」「GW を飛ばす」「31 日を後にずらすと月をまたぐ」がある。
- **祝日データ**
  - 大もとは内閣府の syukujitsu.csv（1955 年〜翌年分。翌年の分は前年の 2 月に載る）。春分・秋分の正式な日は国立天文台が毎年 2 月に発表する。
  - holiday_jp（MIT）は 2050 年まで入っているが、先の春分・秋分は予測。shogo82148/holidays-jp（MIT）は毎日 GitHub Actions で内閣府の CSV を見て、変われば PR を作る。
  - 計算で出す方式は、2019 年や五輪の年のような臨時の祝日が抜ける。
  - **うちに合うやり方**: Supabase に祝日の表を持ち、毎年 2 月以降に内閣府の CSV で更新する。先の年は計算で埋める。12/31〜1/3 の銀行休みは別の印にする。
- 和暦を扱うリポジトリは見つからなかった。

## 5. 取り込み・自動分類

- **カード明細・MF の CSV の取り込みと突き合わせ**（KakeiMatch、MIT）
  - 候補: 日付が前後 7 日以内、金額の差が 100 円か 3% の大きいほう以内。
  - 自動で一致: 金額 55%・日付 25%・店名 20% の点数。金額が同じ・前後 2 日・店名の似ている度合い 0.72 以上、さらに点数 0.88 以上で、双方の第 1 候補かつ次点との差 0.15 以上（`docs/LOCAL_RECONCILIATION.md` で確認）。確認候補の並びは別の重み（金額 55%・日付 30%・支払元 10%・店名 5%）で上位 3 件。
  - 同じ日・同じ金額・同じ店名が複数の支払元にあれば自動にしない。一度判断した取引は別の明細に使い回さない。一致は取り消せる。
  - 「不正利用？」の印: 1〜500 円の見慣れない店のあと翌日・翌々日に 1 万円以上、同じ日に 3 件以上など、カードの不正利用の兆しを知らせる（自動では何も変えない）。
  - MF から: 「計算対象」オフと「振替」の行は取り込まない。MF の ID を残し、なければ内容のハッシュで重複を判定。
  - 楽天は UTF-8 BOM 付きで 11 列と 12 列の 2 種類。PayPay の CSV の文字コードは、公式の Excel での開き方の案内からは UTF-8、割り勘のリポジトリでは Shift_JIS の扱いもあり食い違う（「UTF-8 → だめなら cp932」で両方読む）。モバイル Suica の CSV には年がない。
- 行の重複判定: 日付・金額・正規化した店名の SHA-256（RecoFi）。似た記録: 金額 10 円か 2% まで・日付 ±3 日（yuuri22）。
- **店名辞書**（home-pocket-app、Apache-2.0）: 全角→半角、半角カナ→全角、カタカナ→ひらがな、「・」と空白を除く。うちの `InputHints.normalize` は空白と大文字小文字だけなので、ここを足すとメモの学習が当たりやすくなる。
- **カテゴリの学習**（KakeiMatch `docs/LOCAL_CATEGORY_LEARNING.md`）: 同じ店名・品目で、別々のレシートで同じカテゴリが 3 件以上かつ一致率 80% 以上のときだけ自動で入れる。品目を店名より優先し、いろいろなカテゴリが混ざる店は店名だけで決めない。適用したときは「分類の理由」（根拠の件数と一致率）を残して見せ、設定でルールを無効化・上書きできる。学習の履歴は外に送らない。
  - うちの `categoryForMemo` は 1 件でも一致すれば入れる。自分でカテゴリを選んだら上書きしない作りなので害は小さいが、「3 件以上・80% 以上」にすると、たまたまの 1 件で外れるのを防げる。
- **固定費を見つける**（mf-dashboard、MIT。`packages/analytics/src/recurring-candidates.ts` で確認）: 過去 12 か月、間隔は 3 か月まで、毎月なら 2 回・それ以外は 3 回以上。日は中央値、前後 3 日を許す。「振替」「賞与」は除く。
- **通知から下書き**（kake-bo、考え方だけ）: PayPay は「取引が完了しました。」「金額：N円」「店舗名：」を正規表現で取る。Play の審査での扱いは未確認。

- **KakeiMatch のほかの設計文書**（`docs/`。MIT）
  - 口座間の振替: 2 つの記録を結び付けて持ち、一覧には振替元の 1 件だけを「振替」と出す。月の支出に入れない（§15 の振替・カード引き落としの参考）。
  - 給与明細: 手取りの収入 1 件だけを記録し、控除は支出にしない。同じ月・同じ勤務先の収入があれば警告する。AI に送る前に、氏名・口座番号などを利用者が黒く塗る。
  - 月の予算: まず全体の予算だけを決め、カテゴリ別は任意。カテゴリ別を使うなら合計を全体と同じにしないと保存できない。うちの `budgets` も `category_id` が null で全体を表せるが、合計を合わせる決まりはない。

## 6. Supabase・Android の開発記から（Qiita・Zenn・note）

- **RLS**: 弾かれても 0 件・200 が返り、エラーにならない（ennagara128、cotty）。ポリシーのないテーブルをサブクエリで見て空になる例も（cotty、2026-03-25）。うちは DB 側のテストがあるので、足りないのはクライアントで「0 件」を見張るログ。
- `auth.uid()` を `(select auth.uid())` にすると行ごとの評価を避けられる（ReceiptNote）。家族の規模では効果は小さい。
- **オフライン**: Supabase に組み込みの同期はない。送信待ちキュー（同じ記録の変更は 1 つにまとめる、古い順に送って失敗したら止める、再試行の上限）と、受け取り（画面を開いたとき・戻ったとき・Realtime）を分ける（cotty、2026-03-13）。範囲は最初に絞る（Sansan、DroidKaigi 2026）。うちの `client_request_id` と `version` がそのまま使える。
- **Realtime**: 受け取るにも SELECT のポリシーが要る。通知のたびに全件を取り直すと通信量が人数分増える（taski_app）。届いた差分を画面に当てる。うちは削除も status の更新なので扱いやすい。
- **ウィジェット（Glance）**: 定期更新は 30 分より短くできない。保存したときにアプリから更新する。入力画面を直接開ける（morayl、ko2ic）。日本の家計簿で Glance の開発記は見つからなかった。
- **通知**: AlarmManager は省電力で消える。WorkManager で同じ予約を 1 つに保ち、翌日分を予約し直す（nawa_10half）。家族へのプッシュは端末トークンの表・失効した端末の無効化・二重送信を防ぐキー（cotty）。
- **supabase-kt の実例**（どれもライセンスなし。考え方だけ）
  - JunzoM/EldiaAndroid-public `FridgeViewModel.kt`: 複数テーブルの変更通知をまとめて 800ms 待ってから 1 回だけ同期する。接続状態を「LIVE」表示にし、つなぎ直したら取りこぼし分を同期し直す。画面を閉じたらチャンネルを外す。
  - 同 `core/Offline.kt`: 送れなかった記録を保存し、401・JWT 期限切れも圏外と同じく再送の対象にする（捨てない）。重複エラー（23505）は「前回の送信が届いていた」とみなす。うちの `client_request_id` の一意制約とそのまま組み合わせられる。
  - tanuki276/SANPO-ROAD: Room + supabase-kt。端末の時刻で「最後に書いた方が勝つ」。2 人が同じ家計簿を直すうちには向かず、`version` で比べる今の方が安全。
  - kawamonn91/ttech-store `GoogleSignInHelper.kt`: Credential Manager で Google の ID トークンを取り、Supabase に渡す。nonce は Google に SHA-256 したもの、Supabase に元の値を渡す（同じ値だと不一致エラー）。`setServerClientId` は Web 用のクライアント ID。端末に Google アカウントがなければ「Google でログイン」画面に切り替える。
- **家計簿のウィジェット**: 日本の Kotlin の家計簿 104 件のうち 2 件、どちらも Glance。
  - t-kume-dev/kakeibo: 残高と今月の支出・収入、タップで記録画面。書いたら `updateAll` で描き直す。ただし月替わりで 0 に戻す処理がない（月の集計は年月をキーにして持つべき）。

- うちの繰り返しは、日がない月は月末にする（`least(day_of_month, last)`）、`unique (recurring_id, occurrence_date)` で同じ回の二重作成を防いでいる。
- **ユーザーの集め方**: レビュー依頼のモーダルは効果ゼロ（Warikani）、早く出しすぎると平均が下がる。広がるのは使う人どうしの紹介（Walica）。受け取る側は登録不要にする（タテカリ、TATEKA）。
- 家族が本番を毎日使う前に、本番と STG を分けた（なぺ）。

## 7. 日本ならではの作り

- 精算の結果を **LINE に貼る文面**で送るのが中心の操作（tabiwari、smart-warikan など）。Android では `ACTION_SEND` で `jp.naver.line.android` を指定し、なければ普通の共有（TatekaeMaru）。
- 文面の型: tabiwari は【名前 の精算】「▼ 送金してください」「A → B　¥1,000」、全部すめば「精算はすべて完了」、単位でまとめたら注記。**合計や各自の額はオンにしたときだけ載せる**。TatekaeMaru は精算結果・各自負担額・明細・合計を全部載せる。
  - うちの案: 【グループ名 ○月の精算】→「▼ 送金してください」→「A → B　¥」→「次は○○さんが払うとつり合います」→ 単位の注記。個人の額は初期値では載せない（家族のお金を LINE に流しすぎない）。
- LINE 公式アカウント（Bot を作る場合）: 無料プランは月 200 通。送られた発言への返信は数えない。Bot から自分で送ると送り先の人数分数える（LINE Developers の料金の資料）。うちはアプリから共有するだけなので関係しない。
- PayPay
  - 個人間の送金で、金額や相手を渡してアプリを開く公式の方法は見つからなかった。PayPay for Developers の「アプリコール」は加盟店の決済用。pairbo の `paypay://` も公式の資料にはない。
  - LINE のトークの「送る・受け取る」から PayPay で送れる（2024 年 10 月のニュース。公式ヘルプは未確認）。精算の文面を LINE に送れば、そのトークで払える。
  - 非公式の操作ライブラリは規約上使わない。
- 他のアプリのまねしない点: haraiai は期間の精算を支出の日付ではなく記録した日時で区切っている（あとでまとめて入れると別の期間に入る）。KoheiSeki は人を足したときに前の人の額を直さず、合計が合うか確かめていない。
- 子どものおこづかい: 子が申請して親が承認、台帳は書き足すだけ（tsumiki、MIT）。

  - 同じ日の並びは作成時刻順（`Repo.kt` で `occurred_on` → `created_at` の降順）。対応済み。

  - バックグラウンドから戻ったときのセッション切れは、うちも実機で確かめておく。

## 7c. 高齢の家族・子ども向けの使いやすさ

家計簿で、日本語で、ここまで作り込んだリポジトリはほとんどない（「らくらくモード」「シニア向け」などで家計簿は 0 件）。

- yo5uke/subkan（Compose、ライセンスなし。考え方だけ）: 「約」と金額を別の部品で描いても、`clearAndSetSemantics { contentDescription = … }` で読み上げを 1 回にまとめる。
- KakeiBonByRust（MIT）: 文字サイズ 小／中／大／カスタム（10〜30px）。
- tetlabo/msoffice_UD_color（MIT）: カラーユニバーサルデザインの推奨配色（#FF4600・#FFF100・#03AF7A・#005AFF・#990099・#804000・#84919E など）。カテゴリの色の候補。
- ふりがな: mainrs/android-compose-furigana（MIT、2024 年から更新なし）。
- yukimemi/tsumiki（MIT、子ども向け）: 端末の「動きを減らす」で演出を止める。順位は「あと n コインで おいつくよ」だけで、最下位や差は見せない。
- **うちへの案**
  - `Money.spoken(yen)`（「12,000円」「マイナス 12,000円」）を作り、金額の部品で読み上げを固定する。うちの `Money.format` はマイナスに U+2212 の「−¥」を使っているので、TalkBack がどう読むかを実機で確かめる。 今は金額に読み上げ用の説明がなく（`semantics` はコインボックスとエラー表示だけ）、コインボックスの説明は「○○の貯金箱 n%・100円玉 n枚」で貯金額そのものを読まない。

  - 初期カテゴリの色を UD 配色で見直し、文字と背景が 4.5:1 以上かの単体テストを置く（前回、薄い文字色は #646973 に直してある）。
  - 「かんたんモード」: 入力を「金額→カテゴリ→記録」だけにし、ほかは前回の値のまま隠す（今の「くわしく」を閉じた状態に近い）。コインボックスの動きを控えめにする。

### すでにできていること（確認済み）
